## 二、关键缺陷详解

### 缺陷 1（严重）：「队列 + 暂停 + 置顶」整套未实现
- **现象**：`paused` / `priority` 字段已加进 `batches` 表（`database.py` 迁移），`pause_batch` / `pin_batch` 端点也写了，但全仓库**没有任何代码读取这两个字段**（已 grep 确认：仅写入，无 `ORDER BY priority`、无 `WHERE paused=0` 的消费点）。
- **根因**：没有全局队列/调度器。当前流程是 `upload_tab.create_and_process` 在创建批次后**立即**调用 `process_batch(bid)`，每个批次各跑各的 `TaskPoller`（每次请求 `new` 一个实例，实例内 `_tasks` 不跨请求共享）。
- **后果**：
  - R10 FIFO 队列不存在——"按添加时间排队"只是文案。
  - R13 "暂停未开始队列"无效——`paused` 写了但没人跳过它。
  - R14 "置顶优先级"无效——`priority` 写了但没人按它排序。
- **修复方向**：新增一个常驻后台调度器（如 `app/services/queue_scheduler.py`，在 `main.py` lifespan 启动），周期性 `SELECT ... FROM batches WHERE status='created' AND paused=0 ORDER BY priority DESC, created_at ASC LIMIT ?`，按 `max_concurrent_conversions` 取一批启动；`process_batch` 改为只把批次交给调度器而不是直接跑。

### 缺陷 2（严重）：任务列表 UI 处于被否决状态
- 当前 `tasks_tab.py` 用「HTML 表格 + 内嵌 JS 复选框 + 隐藏 Textbox（#_sst / #_jst）」方案，依赖 Gradio 内部 DOM（`#_sst textarea`）做状态同步，脆弱且交互别扭（跳转需"点链接 + 点按钮"两步）。
- 用户已明确否决（"更丑甚至都不能使用"），**这是当前最高优先级的待修项**。
- 建议用 Gradio 原生组件稳定实现：
  - 用 `gr.Dataframe`（可 `interactive` 的多选 bool 列）或 `gr.CheckboxGroup` 列出批次，首列即 ID；
  - ID 用 `gr.Button`/`gr.Dataframe` 行点击 → 直接 `selected_batch_id` + `tabs.select`，实现"点击/双击即跳转"，不再绕隐藏文本框；
  - 「操作」列/操作区：删除选中、开始处理、暂停、置顶、导出。

### 缺陷 3（中等）：启动恢复不完整
- `main.py` lifespan 把 `processing → created`，但恢复后**没有触发重新处理**。若调度器（缺陷1）落地，恢复阶段应把这批 `created` 批次交给调度器即可自动续跑；否则它们会永远闲置。

### 缺陷 4（轻微）：死代码 / 过时注释
- `api_client.py::download_source_files`（268–275 行）仍在调用已删除的 `/batches/{id}/download-source`，属死代码，建议删除，避免误用。
- `api_client.py::get_batch_table_csv` 的 docstring 写"含源文件路径列"，与当前实现（已去掉源路径）不符，需更正。
- `get_batch_status` 每次都 `TaskPoller(...)` 只为调用纯读取的 `get_status`，额外构造 `DoclingService`/`LLMService` 实例，浪费；可改为直接查 repo。

### 缺陷 5（轻微）：潜在的重复处理竞态
- `process_batch` 每次 `new TaskPoller` 并 `start_processing`，实例级 `_tasks` 去重不跨请求；对同一 `created` 批次并发点击"开始处理"存在小概率双开协程。可在入口用全局锁/状态校验收紧（配合调度器后此问题自然消失）。

## 三、已确认可用的部分（保留）
- 导出链路：base64 HTML 缩略图表、CSV（序号+文件名+字段、BOM）、单文件/批次 ZIP 结果包、JSON。
- 重试链路：批次级重置重跑、单文件 `rerun-ocr`、汇总表 `rerun`。
- 数据层：SQLite 表结构、WAL、触发器更新 `updated_at`、软删除、迁移脚本健壮。
- 详情页：批次汇总表 Markdown 渲染、单文件原图/OCR/对应行、4s 自动刷新。
- 设置页：`/config`、`/config/llm-models`、`/config/test-llm` 端点齐备且与前端引用一致。
- 上传：多文件/ZIP、自动命名、`.webp` 支持、创建即清空输入。

## 四、建议修复路线（按优先级）
1. **P0 重写任务列表 UI**（`tasks_tab.py` + `__init__.py` 接线）：Gradio 原生组件，首列勾选、ID 点击直达详情、操作区按钮稳定可用。
2. **P0 落地全局队列调度器**：`queue_scheduler.py` 在 lifespan 启动，按 `paused=0` 且 `ORDER BY priority DESC, created_at ASC` 取 `created` 批次，受 `max_concurrent_conversions` 限流；让 R10/R13/R14 真正生效。
3. **P1 恢复即续跑**：调度器启动时自然消费 lifespan 恢复的 `created` 批次。
4. **P2 清理**：删除 `download_source_files` 死代码、修正 docstring、优化 `get_batch_status` 实例构造。
5. **P2 收口**：确认 `webp` 在 Docling/PIL 链路确实可解析（当前仅前端接受，后端未显式校验）。
